# 機械学習モデルのトレーニング

## 機械学習の全体の流れ

1. ビジネス要件
2. データ準備
3. MLモデル開発 <- SageMaker
4. デプロイ
5. モニタリング

## MLモデル開発

1. 目的の明確化: MLでどんな問題を解決したいのか
2. モデリングアプローチの選択: 目的に最適なモデルの種類を選択
3. モデルのトレーニング: トレーニングデータを与えて賢く育てる
4. モデルの改良: HPOなどで潜在能力を引き出す
5. モデルの評価: パフォーマンス分析、解釈性

## モデリングアプローチの選択

- 回帰 (Regression)
  - 何らかの数値を予測する問題
  - 「金額」「量」など
  - 過去のデータから、数値とそれに関連する要因の関係性を学習
- 分類 (Classification)
  - データを「クラス」「カテゴリ」に属するかを予測する問題
  - 「スパムメールかどうか」「病気の有無」など
  - YES/NO: 2クラス分類、3クラス以上: 多クラス分類
- クラスタリング (Clustering)
  - あらかじめ正解のラベルが与えられないデータの中から、似た性質を持つ同士を自動的にグループに分ける
  - 教師データ（正解ラベル）がないため、データの隠れた構造やパターンを見つけることが目的

それ以外でも

- 推薦システム
- 時系列予測
- 自然言語処理
- ...

### アルゴリズム選択の考え方

例: 分類問題はわかったけど、アルゴリズムは何を選べばいいの？

- アルゴリズムとは？
  - データから学習するための手順やルールのこと
  - たくさんのアルゴリズムがあり、得意な問題や性格・使いどころが異なる

アルゴリズム選択のポイント

1. データの量と質
   - 学習データの量は十分か
   - データの次元数（特徴量の数）は多いか・少ないか
   - データにノイズはないか
   - これらの要素によって、上手く機能するアルゴリズムが変わる
2. 求められる予測精度と解釈性
   - 精度と解釈はしばしばトレードオフの関係にある
   - 業種によっては説明責任が重要 -> 解釈性の高いアルゴリズムが好まれる
   - ビジネスで使う場合「なぜこの予測が出たのか」を説明できることが重要な場合もある

経験を積む内に、どのアルゴリズムがどんな問題に向いているかがわかってくる

### SageMaker 組み込みアルゴリズム

多くの機械学習アルゴリズムは、

- 数学的な背景が複雑
- 効率的に実装するには、専門的な知識と多くの時間が必要

SageMakerは、機械学習のプロセス全体をサポートしてくれる、統合サービス。
代表的な **組み込みアルゴリズム** が使える

- 線形学習
- XGBoost
- LightGBM
- 画像分類
- 物体検出
- 時系列予測

### 組み込みアルゴリズムのメリット

1. 環境構築の手間が省ける
     - 依存関係や環境構築 (プロビジョニング) の手間がない
     - 依存関係内のバージョンが合わない、ライブラリがインストールできない等の悩みがなくなる
2. アルゴリズムの実装不要
     - 自分でアルゴリズムのコードを書く必要がない
     - データさえ用意すれば、すぐに試すことができる
3. 最適化済みで高性能
     - 大量データや分散学習にも対応

## モデルのトレーニング

- トレーニングデータを与えて、モデルがパターンやルールを自動的に学習するプロセス
- データセットを3つの部分に分割することが一般的
  - 過学習を防ぎ信頼できるモデルを作るためには、データの分割は鉄則
    - 学習データ (Training Data): モデルの学習に使用。60-80%程度が一般的
    - バリデーションデータ (Validation Data): 学習の進捗やハイパーパラメータの調整に使用。10-20%程度が一般的
      - 汎化性能：未知のデータに対してどれだけ正確に予測できるかを示す指標
    - テストデータ (Test Data): 最終的なモデルの性能評価に使用。10-20%程度が一般的
      - リリースした時の実際のモデルの性能に近い指標

### SageMakerでのトレーニングジョブの実行

SageMakerを使うと、複雑なインフラ管理・環境構築の手間を省いて、トレーニングジョブを簡単に実行できる

1. 学習データの準備とアップロード
     - 通常はS3にアップロード
2. 学習スクリプトの準備
     - 組み込みアルゴリズムを使う場合は、スクリプト不要
     - カスタムアルゴリズムを使う場合は、トレーニングスクリプトを用意
     - SageMakerのスクリプトモードを使うと、通常のPythonスクリプトでトレーニングコードを書くことができる
3. コンテナイメージの選択
     - 組み込みアルゴリズムを使う場合は、SageMakerが提供する既成のコンテナイメージを指定
     - カスタムアルゴリズムを使う場合は、自分でコンテナイメージを作成して指定
4. トレーニングジョブの作成・起動
     - 使用するアルゴリズム（組み込み or カスタム）
     - 学習データの場所 (S3 URI)
     - インスタンスタイプ
     - ハイパーパラメータ: 学習率、エポック数、バッチサイズなど
     - 出力データの場所 (S3 URI): モデルアーティファクトやトレーニングのログが保存される場所
5. トレーニングの実行とモニタリング
  1. 指定されたインスタンスを用意
  2. コンテナイメージをダウンロード
  3. トレーニングスクリプトを実行
       - 組み込みアルゴリズムの場合は、SageMakerが提供するトレーニングコードが実行される
  4. トレーニングの進捗やログをCloudWatch LogsやSageMakerコンソールでモニタリング
6. モデルアーティファクトの保存
     - トレーニングが完了すると、指定したS3バケットに自動的に保存される
     - 次のデプロイや評価のステップで、モデルアーティファクトが利用される

### SageMaker Managed Warm Poolsによるトレーニングの効率化

- トレーニングジョブの起動時に、すぐに利用できるインスタンスをプールしておく機能
- 特徴量やハイパーパラメータのチューニングなど、複数のトレーニングジョブを連続して実行する場合の待ち時間を大幅に削減
- Warm Poolsを設定すると、トレーニングインスタンスが常に一定数プールされ、トレーニングジョブの起動時にすぐに利用できる状態になる
- 結果としてモデル開発のイテレーション（試行錯誤）が高速化される

## ハイパーパラメータチューニング

- パラメータの種類
  - モデルパラメータ: 学習プロセスで自動的に学習されるパラメータ
    - 線形回帰： 回帰係数、切片など
    - NN： 重み、バイアスなど
  - ハイパーパラメータ: モデルの学習プロセスを制御するパラメータ
    - 学習率： モデルの重みを更新する際のステップサイズ
    - エポック数： トレーニングデータ全体を何回繰り返して学習するか
    - バッチサイズ： 一度にモデルに入力するデータの量
    - NNの層の数やノード数などの構造に関するパラメータ
    - 正則化パラメータ： モデルの複雑さを制御するためのパラメータ

- ハイパーパラメータ1つでも、モデルの性能が大きく変わることがある

- ハイパーパラメータのチューニングの理由
  - あるモデルでの最適な組み合わせが、別のモデルでは最適であるとは限らない
  - データセットの特性やモデルの構造によって、最適なハイパーパラメータの組み合わせが異なるため、チューニングが必要
  - チューニングを行うことで
    - モデルの予測精度を最大化できる
    - 学習に必要な時間を短縮できる
    - 過学習を防止し、モデルの汎化性能を向上させることができる

### 代表的なハイパーパラメータチューニングの手法

1. 手動チューニング
     - 経験や直感に基づいて、ハイパーパラメータの値を手動で調整する方法
     - シンプルだが、最適な組み合わせを見つけるのは難しい
     - 初学者には、ハイパーパラメータの影響を理解するための良い方法
2. グリッドサーチ (Grid Search)
     - ハイパーパラメータの値の組み合わせを網羅的に探索する方法
     - 全ての組み合わせを試すため、計算コストが高くなることがある
3. ランダムサーチ (Random Search)
     - ハイパーパラメータの値の組み合わせをランダムに探索する方法
     - グリッドサーチよりも効率的に最適な組み合わせを見つけることができる
4. ベイズ最適化 (Bayesian Optimization)
     - 過去の試行結果を元に、次に試すべきハイパーパラメータの組み合わせを賢く選択する方法
     - より少ない試行回数で最適な組み合わせを見つけることが期待できる

### SageMakerの自動モデルチューニング

ユーザーはSageMakerにチューニングの方針を伝える。

- チューニングするハイパーパラメータとその値域
- 最適化したい評価指標
  - 例: バリデーションデータでの損失関数の最小化、F1スコアの最大化など
- 試行するジョブの最大数や、並列で実行するジョブの数などのリソース制限

SageMakerは、内部ではベイズ最適化などのアルゴリズムを使って、効率的にハイパーパラメータの組み合わせを探索する。

## 訓練中のトラブル解決 (1) : 過学習

### 過学習とは

モデルが学習データに対してあまりにも適合しすぎて、未知のデータに対応できなくなっている状態。
学習データのノイズや偶然のパターンまで学習してしまうため、汎化性能が低下する。

- 過学習の症状
  - 学習データに対する精度が非常に高い
  - バリデーションデータやテストデータに対する精度が低い -> 汎化性能が低い

- 機械学習モデルを作る目的
  - 過去のデータから学んだパターンを使って、将来の未知のデータに対して正確な予測をすること

- 過学習が起こりやすい条件
  - モデルが複雑すぎる（パラメータが多すぎる）
  - 学習データが少なすぎる
  - 学習データにノイズが多い
  - 学習を長時間続けすぎる（エポック数が多すぎる）

- 学習曲線で過学習を見つける
  - 学習曲線： 学習の進行度と損失関数の値や精度の関係をグラフにしたもの
  - 学習データとバリデーションデータの学習曲線を比較することで、過学習の兆候を見つけることができる
    - 初期段階: 学習データとバリデーションデータの精度がともに上がる
    - 分岐点: 学習データの精度が上がり続ける一方で、バリデーションデータの精度が頭打ちになったり下がり始める
    - 過学習段階: 学習データの精度が非常に高いのに対して、バリデーションデータの精度が低い状態
  - SageMaker では、トレーニングジョブのメトリクスから学習曲線を確認できる

#### 過学習を防ぐ手法

1. 早期停止 (Early Stopping)
     - 学習の途中で、バリデーションデータの性能が向上しなくなったら学習を停止する方法
     - 分岐点を見つけて、過学習が始まる前に学習を終えることができる
       - 検証データの性能が一定期間向上しない場合に学習を停止する設定が一般的
       - 計算リソースの節約にもなる
     - SageMakerの組み込みアルゴリズムの中には、早期停止をサポートしているものもある
     - カスタムアルゴリズムを使う場合は、トレーニングスクリプト内で早期停止のロジックを実装することも可能

2. ドロップアウト (Dropout)
     - ニューラルネットワークのトレーニング中に、ランダムに一部のノードを無効化する方法
     - ある確率でノードを無効化（例: 中間層を50%の確率で無効化）することで、モデルの過学習を防ぐ
     - ドロップアウトが有効な理由
       - 共依存の防止： モデルが特定のノードや特徴量の組み合わせでしか機能しない状態を防ぐ
       - アンサンブル効果： 毎回異なるノードの組み合わせで学習することで、実質的に複数のモデルを同時に学習しているような効果が得られる
     - ドロップアウトの実装
       - `nn.Dropout(p=0.5)` のように、ドロップアウトの確率を指定して使用する
     - ドロップアウトの注意点
       - ドロップアウト率が高すぎると、モデルが十分に学習できなくなる可能性がある

3. 正則化 (Regularization)
     - モデルの複雑さを制御するための手法。MLの世界では王道
       - 複雑すぎると、細かいノイズや偶然のパターンまで学習してしまうため、過学習のリスクが高まる
     - 正則化は、(予測誤差＋ペナルティ) を最小化するようにモデルを学習させる方法
       - 予測誤差: モデルの予測と実際の値の差を表す指標。例： 平均二乗誤差 (MSE)、クロスエントロピー損失
       - ペナルティ: モデルの複雑さに対して課される罰則。モデルの重みが大きくなりすぎないようにするためのもの
     - L1正則化（Lasso）: モデルの重みの絶対値の合計にペナルティを課す方法
       - 不要な特徴量の重みをゼロにする（不要なものは完全に切り捨てる）効果がある
       - 大量の特徴量がある場合に、重要な特徴量を自動的に選択するのに役立つ
     - L2正則化（Ridge）: モデルの重みの二乗和にペナルティを課す方法
       - どの特徴量も完全にゼロにはしないが、極端な重みを抑える効果がある
       - 一般的に、学習が安定し、バランスよく対応できるモデルになりやすい
     - SageMakerの多くの組み込みアルゴリズムは、L1やL2正則化のハイパーパラメータをサポートしている

### SageMaker Debuggerによる過学習の自動検出

実際のプロジェクトでは「いつ過学習が起きているのか」「どの対策を取ればいいのか」を判断するのは難しいことがある。
SageMaker Debuggerは、トレーニングジョブの実行中に、過学習の兆候を自動的に検出して通知してくれる機能を提供している。

1. 自動的なメトリクス監視
     - トレーニングジョブのメトリクスをリアルタイムで監視
     - 学習中の損失、精度、勾配、重みの分布など
2. 組み込みルール
     - 例： 過学習の兆候を検出するための組み込みルール (Overtraining) が用意されている
3. カスタムルール
     - ユーザーが独自のルールを定義して、特定の条件でアラートを出すことも可能
4. リアルタイムアラート
     - 過学習の兆候が検出された場合、CloudWatchやAmazon SNSを通じてリアルタイムで通知
5. 自動アクション
     - 例えば、過学習が検出されたら、自動的に停止するアクションを設定

## 訓練中のトラブル解決 (2) : NN特有の問題

- NNの学習が上手く行かない場合の代表的な問題
- 解決の糸口・Amazon SageMaker Debuggerの活用方法

### 損失が振動・高止まりする

- 学習率 (Learning Rate)
  - 内部のパラメータ（重みやバイアス）を更新する際のステップサイズ

- 損失関数の値が大きく上下に振動して、一点に収束しない
  - 学習率のスケジューリング
  - 学習率減衰

### 勾配消失・勾配爆発

- 勾配
  - 損失関数を各パラメータで微分したもの
  - 勾配の大小でパラメータの更新量の大小が決まる

- 誤差逆伝播法 (Backpropagation)
  - 勾配を計算して、ネットワークの重みを更新するためのアルゴリズム
  - 出力層から入力層に向かって、誤差を逆方向に伝播させながら勾配を計算する
  - 層があまりにも深いと、勾配が非常に小さくなったり、逆に非常に大きくなったりすることがある

- 勾配消失問題 (Vanishing Gradient Problem)
  - 勾配が非常に小さくなり、重みの更新がほとんど行われなくなる現象
  - 特に深いネットワークで発生しやすい

- 勾配爆発問題 (Exploding Gradient Problem)
  - 勾配が非常に大きくなり、重みの更新が過剰に行われる現象
  - 学習が不安定になり、損失が発散することがある

### Amazon SageMaker Debugger による問題の自動検出

- Amazon SageMaker Debugger
  - 勾配消失・勾配爆発といった問題を検知するための組み込みルールが用意されている
  - トレーニング中にこれらの問題の兆候をリアルタイムで検出し、アラートを出すことができる

**代表的な組み込みルール**

ルールを有効にすると、トレーニングジョブのメトリクスをリアルタイムで監視し、問題の兆候を検出した場合にアラートを通知することができる。

- VanishingGradient: 勾配消失を検出
- ExplodingTensor: テンソル（勾配や重みなど）の値が発散あるいは爆発していることを検出
- LowGPUUtilization: GPUの使用率が低いことを検出（学習が上手く行っていない可能性がある）
- StalledTrainingRule: 学習が停滞していることを検出（損失が一定期間改善しないなど）

```python
# SageMaker Debuggerの組み込みルールの例

built_in_rules = [
    Rule.sagemaker(
      base_config=rule_configs.vanishing_gradient(),
      rule_parameters={
        "threshold": "0.00001",  # 勾配の値が0.00001以下の場合にアラートを出す
      },
      collection_to_save={
        CollectionConfig(
          name="gradients",  # 勾配の値を収集するコレクション
          parameters={
            "save_interval": "500"  # 500ステップごとに勾配の値を保存
          }
        )
      }
    )
]
```

**Debuggerのプロファイリング機能**

- トレーニングジョブの実行中に、CPUやGPUの使用率、メモリ使用量、I/O待ち時間などのシステムリソースの利用状況を詳細にプロファイリングすることができる
- プロファイリングデータを基に、ボトルネックの特定やリソースの最適化を行うことができる

## 大規模モデルの分散トレーニング

- 大規模なモデルや大量のデータを扱う場合、単一のGPUマシンでのトレーニングが困難になることがある
  - 単一のマシンでは、学習が終わるのに何週間・何か月もかかる
  - モデルが大きすぎるため、単一のマシンでは処理しきれない

- ポイント
  - なぜ分散トレーニングが必要かの考え方
  - Amazon SageMakerの分散トレーニングのサポート内容

### なぜ分散トレーニングが必要か

- 個々のコンピューティングデバイスの物理的限界
  1. 計算能力の限界
  2. メモリ容量の限界
        - VRAM: GPUのメモリ容量。16GB, 32GB, 48GBなど
        - ミニバッチ（一度に処理するデータの量）がひとつのGPUのVRAMに収まらない場合、そもそも学習すら開始できない
- これらの突破するために、複数のGPUを使った分散トレーニングが必要
  - 複数のGPU・マシンを連携させて、学習作業を並列化・分散化するための仕組み

### 分散トレーニング

- 学習時間の大幅な短縮
- 大規模なモデルやバッチサイズの使用が可能

### データ並列とモデル並列

**データ並列 (Data Parallelism)**

同じモデルのコピーを複数のワーカー（GPU）に配置し、それぞれが異なるデータのバッチを同時に処理する方法。
各ワーカーが独立して計算を行い、定期的に勾配の集約（重みの更新を同期）を行う。

- メリット
  - 実装が比較的シンプル
  - データ量が多い場合に効果的
  - 学習時間の大幅な短縮が期待できる
- デメリット
  - モデル全体が各ワーカーのメモリに収まる必要がある
  - ワーカー間で通信が必要なため、通信遅延が発生する可能性がある

**モデル並列 (Model Parallelism)**

モデルの異なる部分を複数のワーカー（GPU）に分割して配置し、各ワーカーがモデルの一部を処理する方法。
例えば、入力層～第3層はGPU1、第4層～第6層はGPU2、…、第n層～出力層はGPU｛n｝のように分割する。

- メリット
  - 非常に大きなモデルを扱うことができる（モデル全体が単一のGPUのメモリに収まらない場合でも学習可能）
- デメリット
  - 実装が複雑で、モデルの構造に応じた分割方法を考える必要がある

**ハイブリッド並列 (Hybrid Parallelism)**

モデル全体を部分ごとに分けて複数GPUで分担し、さらに各部分ごとに同じモデルをコピーして異なるデータを同時処理することで、両方のメリットを活かす方法。

### SageMaker AI の分散トレーニングライブラリ

データ並列・モデル並列のロジックは複雑で、実装するのは大変。

- ワーカー間の同期処理
- 通信プロトコル
- エラーハンドリング

Amazon SageMaker AIは、分散トレーニングのためのライブラリやフレームワークを提供している。

- モデル並列の実装例 (PyTorch)

```python
import sagemaker
from sagemaker.pytorch import PyTorch

estimator = PyTorch(
    entry_point="train.py",
    instance_type="ml.p3.16xlarge",
    instance_count=2,
    distribution={
        "smdistributed": {
            "modelparallel": {
                "enabled": True,
                "parameters": {
                    "partitions": 2,          # モデルを2つのGPUに分割
                    "pipeline": "interleaved", # パイプライン実行で効率化
                }
            }
        }
    }
)
```

- データ並列の実装例 (PyTorch)

```python
import sagemaker
from sagemaker.pytorch import PyTorch

estimator = PyTorch(
    entry_point="train.py",
    instance_type="ml.p3.16xlarge",
    instance_count=4,              # 4インスタンスでデータを並列処理
    distribution={
        "smdistributed": {
            "dataparallel": {
                "enabled": True,
            }
        }
    }
)
```

分散トレーニングライブラリは以下の処理を自動的・半自動的に行ってくれる。

1. ワーカー間の通信の最適化
     - 勾配を集約する際の通信アルゴリズム（リングリダクション）の最適化
     - 高速なネットワークインターフェースを活用して、通信のオーバーヘッドを最小化
2. データのシャーディング（分割）の自動化
     - データ並列の場合、学習データをワーカー数に応じて自動的に分割して割り当てる
3. チェックポイント処理のサポート
     - 分散トレーニング中に定期的にモデルの状態を保存するためのチェックポイント機能を提供
     - S3に保存されたチェックポイントからトレーニングを再開することができる
4. スケーラビリティの確保
     - 必要に応じて、数十台・数百台といった大規模なGPUクラスターでのトレーニングもサポート

これにより、分散処理の複雑な実装を気にせずに、以下の恩恵を受けることができる。

- モデルのアーキテクチャ設計や実験に集中できる
- 分散トレーニングによる学習の高速化や大規模モデルの学習が可能になる

### インスタンス間通信オーバーヘッドを最小化するための配置戦略

分散トレーニングでは、ワーカー間の通信が頻繁に発生するため、通信オーバーヘッドを最小化することが重要。

1. インスタンスの物理的な配置
     - 同一のアベイラビリティゾーン内でインスタンスを配置することで、通信のレイテンシを低減できる
     - 同一の物理サーバー上に複数のインスタンスを配置することで、さらに高速な通信が可能になることもある
2. 高速ネットワークインターフェースの活用
     - SageMakerでは、インスタンス間の通信に高速なネットワークインターフェース（例: Elastic Fabric Adapter）を利用できる
     - EFAは、低レイテンシで高スループットの通信を提供するため、分散トレーニングの効率を大幅に向上させることができる
3. 効率的な集団通信アルゴリズムの利用
     - 勾配の集約やモデルの同期において、効率的な通信アルゴリズム（例: リングリダクション）を自動的に選択・実行

Amazon SageMaker AI は上記のような最適化を自動的に行うため、複数GPU環境を最大限に活用することができる。

# デプロイと自動化

## リアルタイム推論

データが入力された瞬間にMLモデルが即座に予測を返す仕組み。
今すぐ結果がほしい多くのビジネスシーンで利用。

* EC・メディアのレコメンド
* 迷惑メールフィルタ
* クレジットカード不正検知
* 広告入札
* リアルタイム監視
* 自動運転ナビゲーション
* チャットボット
* 画像認識アプリ

## SageMaker リアルタイムエンドポイント

学習済みのモデルをホストして、HTTPSリクエストに対してリアルタイムで予測を返すスケーラブルで高可用性の推論環境を提供するマネージドサービス。

### 作業の概要

- 学習済みモデルをSageMakerにアップロード
  - 学習済みモデルのアーティファクトをS3に保存し、そのS3 URIを指定してSageMakerにモデルを登録する
- SageMaker AIが自動的にサーバ（インスタンス）をプロビジョニング
  - 指定されたインスタンスタイプと数に基づいて、必要なサーバーリソースを自動的に用意する
- モデルをロードして、推論用のAPIを公開
  - モデルをロードして、HTTPリクエストを受け付けるAPIエンドポイントを公開する
- ユーザーからのリクエストに対して、リアルタイムで予測を返す
  - クライアントからのリクエストを受け取り、モデルを使って予測を行い、その結果をHTTPレスポンスとして返す

インフラの管理やスケーリングはSageMakerが自動的に行うため、ユーザーはモデルのデプロイと推論に集中できる。

### SagaMaker AIエンドポイントの作成

1. モデル (Model) リソースの作成
    1. モデルアーティファクトのS3 URIを指定して、SageMakerにモデルを登録する
    2. 推論コンテナイメージを指定する
2. エンドポイント設定 (Endpoint Configuration) の作成
    1. インスタンスタイプ : `ml.m5.large` など
    2. インスタンス数 : 1台以上。必要に応じてスケールアウト可能
    3. トラフィックのルーティング設定
        - 新旧複数モデルのバージョンを「バリアント」として同時デプロイ可能
        - バリアント： モデルのバージョンや構成の単位。トラフィックの分配比率を指定し、複数バリアントにリクエストを分散させることができる
3. エンドポイント (Endpoint) デプロイ
    1. インスタンスのプロビジョニング
    2. モデルのロード
    3. APIの公開 (HTTPSエンドポイントの設定)
    4. ヘルスチェックの開始： モデルが正常に動作しているかの定期確認

### エンドポイントへのリクエスト/レスポンスの確認

#### 同期推論 (リアルタイム)

Boto3を使って、エンドポイントにリクエストを送るだけ。

```python
import boto3

runtime = boto3.client("sagemaker-runtime")

# 同期リクエストの送信
resp = runtime.invoke_endpoint(
    EndpointName="my-endpoint",
    ContentType="application/json",
    Body=json.dumps({"userId": "12345", "itemId": "67890"})
)
```

レスポンスの例。(商品のレコメンド結果)

```jsonc
{
  "recomendations": [
    {"itemId": "11111", "score": 0.95},
    {"itemId": "22222", "score": 0.90},
    {"itemId": "33333", "score": 0.85}
  ]
}
```

#### 非同期推論 (Async Inference)

- ペイロードが大きい (最大1GB)・推論に時間がかかるケースに対応した推論方式
- `invoke_endpoint_async` はリクエストをキューに入れると即座に返る
  - 呼び出し元はレスポンスをブロッキング待機しない
- 推論完了後、結果は指定したS3バケットに書き込まれる
- 結果の取得方法は2種類

**① S3ポーリングによる取得**

```python
import time
import json
import boto3

runtime = boto3.client("sagemaker-runtime")
s3 = boto3.client("s3")

# 非同期リクエストの送信 (すぐに返る)
resp = runtime.invoke_endpoint_async(
    EndpointName="my-async-endpoint",
    ContentType="application/json",
    InputLocation="s3://my-bucket/input/payload.json",  # 入力データのS3 URI
    InvocationTimeoutSeconds=3600,
)

output_location = resp["OutputLocation"]  # 例: "s3://my-bucket/output/xxxx.json"
bucket, key = output_location.replace("s3://", "").split("/", 1)

# S3に結果が書き込まれるまでポーリング
while True:
    try:
        result = s3.get_object(Bucket=bucket, Key=key)
        predictions = json.loads(result["Body"].read())
        print(predictions)
        break
    except s3.exceptions.NoSuchKey:
        print("推論中... 待機します")
        time.sleep(5)
```

**② SNS通知による取得 (推奨)**

エンドポイント設定時にSNSトピックを指定しておくと、推論完了時にSNSへ通知が届く。
ポーリングが不要になるため、よりイベント駆動なアーキテクチャを実現できる。

```python
# エンドポイント設定時にSNSトピックを指定
sagemaker_client = boto3.client("sagemaker")

sagemaker_client.create_endpoint_config(
    EndpointConfigName="my-async-endpoint-config",
    ProductionVariants=[...],
    AsyncInferenceConfig={
        "OutputConfig": {
            "S3OutputPath": "s3://my-bucket/output/",
            "NotificationConfig": {
                "SuccessTopic": "arn:aws:sns:ap-northeast-1:123456789:inference-success",
                "ErrorTopic":   "arn:aws:sns:ap-northeast-1:123456789:inference-error",
            }
        },
        "ClientConfig": {
            "MaxConcurrentInvocationsPerInstance": 4,
        }
    }
)
```

SNSのサブスクライバー（Lambda等）で `OutputLocation` を受け取り、S3から結果を読み込む。

```python
# Lambda等のSNSサブスクライバー側
def handler(event, context):
    message = json.loads(event["Records"][0]["Sns"]["Message"])
    output_location = message["outputLocation"]  # S3 URI
    bucket, key = output_location.replace("s3://", "").split("/", 1)

    result = boto3.client("s3").get_object(Bucket=bucket, Key=key)
    predictions = json.loads(result["Body"].read())
    print(predictions)
```

## スケーラビリティと高可用性

- SageMakerは、エンドポイントのスケーリングと高可用性を自動的に管理する
- 本番環境では、需要変動や障害に対応できるように、スケーラビリティと高可用性を確保することが重要
  - スケーラビリティとは
    - 需要に応じて処理能力を柔軟に増減できる能力
  - 高可用性とは
    - 障害が発生しても、サービスが継続して利用できる状態を維持する能力

**MLモデルのエンドポイントでスケーラビリティが変動する例**

- 商品の新発売キャンペーンやメディアでサービスが紹介されてアクセスが急増
- 深夜帯にアクセスが全くない
- 月末の締め処理の時だけアクセスが集中

ただし、始めから大量のエンドポイントを用意すると、無駄なコストが発生する可能性がある。
必要に応じてスケールアウトできるようにすることが重要。

## SageMaker AIエンドポイントの自動スケーリング

- トラフィックの増加に応じて、エンドポイントのスケーリングを自動的に行う機能
- CloudWatchのメトリクスを基に、スケーリングのトリガーを設定することができる

### 主に監視されるメトリクス

- InvocationsPerInstance: インスタンスあたりのリクエスト数
- ModelLatency: モデルの推論にかかる時間
- CPUUtilization: CPU使用率
- MemoryUtilization: メモリ使用率

### スケーリングポリシーの設定例

- リクエスト数が1分間平均で800を超えたら、新しいインスタンスを追加
- 500を下回ったら、インスタンスを削除

### スケーリングのベストプラクティス

予測不可能なバーストトラフィックに対応しつつ、無駄なコストを抑えるためのポイント

1. 急激な変更を避ける
2. クールダウン期間を設定する
     - 頻繁なスケーリングを防ぐために、スケーリング後に一定期間待機する
3. 事前にウォームアップする
     - トラフィック増加が予測可能な時は、事前にスケールアウトさせる

### 複数AZへのデプロイによる高可用性

- アベイラビリティゾーン
  - AWSのデータセンターの物理的なロケーションの単位
  - それぞれ独立した電源供給を持ち、障害が発生しても他のAZに影響を与えないように設計されている

SageMakerのエンドポイントをマルチAZデプロイ（複数AZにまたがってデプロイ）することで、次のメリットを得ることができる。

1. 単一AZ障害への耐性
    - あるAZで障害が発生しても、他のAZにデプロイされたインスタンスが引き続きリクエストを処理
2. 負荷分散
    - 複数AZにトラフィックを分散して、全体のパフォーマンスを向上
3. メンテナンス時の無停止
    - AZ毎に順番にメンテナンスできる

SageMakerのエンドポイントは、2台以上のインスタンスを指定すれば、自動的に複数AZにデプロイされる。

### エンドポイント更新時のデプロイ戦略

安全にエンドポイントを更新するためのデプロイ戦略

1. ブルー/グリーンデプロイメント
     - 新しいバージョンのモデルのエンドポイント（グリーン）にデプロイし、テストが完了したらトラフィックをグリーンに切り替え
     - 問題が発生した場合は、すぐにブルーにロールバックできる
2. カナリアリリース
     - 新バージョンに少しずつトラフィックを流していく方法
     - 最初は極小のトラフィックを新バージョンに流し、問題がなければ徐々に増やしていく
     - 問題が発生しても、影響を受けるユーザーが少ないため、リスクを最小化できる
3. 線形リリース
     - カナリアリリースの発展版。時間をかけて段階的にトラフィックを新バージョンに移行していく
     - 時間をかけて慎重に移行したい場合に最適

**デプロイ戦略の選択基準**

| ユースケース | 適したユースケース |
|------|------------------|
| リスクを最小限にしたい | カナリアリリースまたは線形リリース |
| 素早く切り替えたい | ブルー/グリーンデプロイメント |
| 実験的な機能を試したい | カナリアリリース |

## SageMaker サーバレス推論

- サーバレス推論
  - トラフィックが不規則・使用頻度が低いユースケースに最適
- プロビジョニング済み同時実行数  -
  - サーバレス推論の弱点を補う

### サーバレス推論

- 推論リクエストがない間は、コンピューティングリソースに対して課金が発生しない
- リクエストが来た時だけ自動的にリソースを起動して処理 (アイドルコストがゼロ)

**サーバレス推論が有効なユースケース**

1. トラフィックが非常に少ない・断続的
2. トラフィックの予測が難しい
    - サーバレス推論はリクエストに応じて自動的にスケールアップ/ダウンするため、トラフィックの変動に柔軟に対応
3. インフラ管理を極力避けたい
    - サーバレス推論は完全にマネージドなサービスで、インフラのプロビジョニングや管理が不要
4. 開発環境/テスト環境として使いたい
    - 本番環境ほどのスケーラビリティや可用性が必要ない場合、サーバレス推論はコスト効率の良い選択肢

### サーバレス推論のコールドスタート問題

- コールドスタート
  - サーバレス推論はリクエストが来た時にリソースを起動する
  - その際、コンテナの起動やモデルのロードに時間がかかる (数秒〜数十秒程度) ため、応答が遅れてしまう
      1. コンテナ（推論環境）の起動
      2. 必要なライブラリのロード
      3. モデルファイルのロード
      4. モデルの初期化
- なぜコールドスタートは起きる？
  - サーバレスは使わないとき「リソースを完全に開放する」という仕組み
  - リクエストが来たときに初めてリソースを確保してコンテナを起動するため、初回のリクエストは遅くなる

# Appendix

## SageMaker リアルタイムエンドポイント / サーバレス推論 / バッチ変換ジョブ / Lambda Function URLs の選択

### 選択の指針

```
GPU必要 / 常時高スループット / 大規模モデル
  → SageMaker リアルタイムエンドポイント

CPU推論で十分 / トラフィックが断続的 / MLエコシステムと統合しつつアイドルコストを抑えたい
  → SageMaker サーバレス推論  (← コスト重視の本番MLではまずここを検討)

リアルタイム応答が不要 / 大量データを一括処理したい / エンドポイントを常設したくない
  → SageMaker バッチ変換ジョブ

軽量モデル / プロトタイプ / ML以外の処理と同居 / SageMaker管理外
  → Lambda (Docker) + Function URLs
```

判断の核心は**リアルタイム性の要否・コスト構造・MLエコシステム統合の有無**の3軸

| | リアルタイム性 | コスト構造 | MLエコシステム統合 |
|--|-------------|-----------|-----------------|
| SageMaker リアルタイムエンドポイント | ◎ 常時起動 | インスタンス稼働時間課金（アイドル時も課金） | ◎ フル統合 |
| SageMaker サーバレス推論 | ○ コールドスタートあり | リクエスト数×処理時間（アイドル無課金） | ◎ フル統合 |
| SageMaker バッチ変換ジョブ | ✕ 非リアルタイム（非同期一括） | ジョブ実行時間のみ課金（完了後インスタンス自動終了） | ◎ フル統合 |
| Lambda (Docker) + Function URLs | ○ コールドスタートあり | リクエスト数×実行時間（アイドル無課金） | △ 自前実装 |

### 詳細比較

| 観点 | SageMaker リアルタイムエンドポイント | SageMaker サーバレス推論 | SageMaker バッチ変換ジョブ | Lambda (Docker) + Function URLs |
|------|--------------------------------------|--------------------------|---------------------------|----------------------------------|
| **推論レイテンシ** | 低レイテンシ（常時起動） | コールドスタートあり（数秒〜） | 非リアルタイム（分〜時間単位） | コールドスタートあり（数秒〜十数秒） |
| **コールドスタート** | なし | あり | なし（ジョブ起動に数十秒〜） | あり |
| **GPUサポート** | ◎ ネイティブ対応（`ml.p3`, `ml.g4dn` 等） | ✕ 非対応 | ◎ ネイティブ対応 | ✕ 非対応 |
| **モデルサイズ上限** | 制限なし（数十GB〜） | メモリ上限まで（最大 **6GB**） | 制限なし | コンテナイメージ最大 10GB |
| **メモリ上限** | インスタンスタイプに依存 | 最大 **6GB** | インスタンスタイプに依存 | 最大 10GB |
| **入力データサイズ** | 最大 6MB（同期）/ 最大 1GB（非同期） | 最大 **4MB** | **S3上のデータなら制限なし** | 最大 6MB |
| **同時実行数** | Auto Scaling で柔軟に対応 | 最大 **200 concurrency/endpoint** | インスタンス数×並列度で制御 | アカウント上限 1,000（リージョン共有） |
| **推論時間の上限** | 実質制限なし（同期 60秒、非同期は別） | 最大 **60秒** | 制限なし | 最大 15分 |
| **コスト構造** | インスタンス稼働時間課金（**アイドル時も課金**） | リクエスト数×処理時間（**アイドル無課金**） | **ジョブ実行時間のみ課金**（完了後自動終了） | リクエスト数×実行時間（**アイドル無課金**） |
| **低トラフィック時のコスト** | 高い（常時インスタンス稼働） | 低い | 最も低い（使わなければゼロ） | 低い |
| **高トラフィック時のコスト** | インスタンス台数に比例 | リクエスト増加で高騰しやすい | データ量に比例（予測しやすい） | リクエスト増加で高騰しやすい |
| **エンドポイント管理** | 常設が必要 | 常設が必要 | **不要**（ジョブ単位で起動・終了） | 常設が必要 |
| **インフラ管理** | マネージド（インスタンス指定が必要） | フルマネージド（インスタンス指定不要） | マネージド（インスタンス指定が必要） | コンテナイメージのビルド・管理が必要 |
| **A/Bテスト・カナリア** | バリアントで標準サポート | バリアントで標準サポート | ✕ 対象外（バッチ処理のため） | 自前実装が必要 |
| **モニタリング** | Debugger / Model Monitor 統合済み | Model Monitor 統合済み | CloudWatch Logs / S3出力で確認 | CloudWatch Metrics のみ（自前構成） |
| **MLパイプライン連携** | SageMaker Pipelines と密に統合 | SageMaker Pipelines と密に統合 | SageMaker Pipelines と密に統合 | 別途連携ロジックが必要 |
| **フレームワークサポート** | TF / PyTorch / SKLearn 等を標準コンテナで提供 | TF / PyTorch / SKLearn 等を標準コンテナで提供 | TF / PyTorch / SKLearn 等を標準コンテナで提供 | 任意（Docker で自由に構成） |
| **実装のしやすさ** | 中：モデル登録・エンドポイント設定の概念を理解する必要あり | 中：リアルタイムとほぼ同じ手順。インスタンス指定が不要な分シンプル | 中：ジョブ設定はシンプルだがS3 I/O設計が必要 | 高：Lambdaハンドラ＋Dockerイメージを書けばよく、AWS特有の概念が少ない |
| **学習コスト** | 高：SageMaker固有の概念（モデルリソース・エンドポイント設定・バリアント等）を習得が必要 | 中：リアルタイムのサブセット。SageMaker基礎知識があれば追加コスト小 | 中：リアルタイムのSageMaker知識があれば転用しやすい | 低：Lambda・Docker・HTTPの知識で足りる。MLエンジニア以外でも扱いやすい |
| **適したユースケース** | 本番ML推論（高負荷・大規模・GPU） | 低〜中頻度・断続的トラフィック・CPU推論 | 定期バッチ・大量データの一括予測・ワンショット推論 | 軽量モデル・プロトタイプ・非ML用途との同居 |

### バッチ変換ジョブの適用ポイント

リアルタイム応答が**不要**で、以下の条件に当てはまる場合はバッチ変換ジョブが最適解。

| 条件 | 説明 |
|------|------|
| 定期的な一括予測 | 日次・月次などのスケジュールで大量レコードを処理する（需要予測、スコアリング等） |
| ワンショット推論 | 学習直後に同じデータに対して一度だけ予測を実行したい |
| 入力データが大きい | S3上のデータをそのまま使えるため、ペイロードサイズ制限を気にしなくてよい |
| エンドポイントを常設したくない | ジョブ完了後にインスタンスが自動終了するため、管理・コストが最小 |
| 推論結果をS3に保存すればよい | 結果をS3に書き出し、後段の処理（ETL・BI等）で読み込む構成に向いている |

```python
# バッチ変換ジョブの実行例
import sagemaker
from sagemaker.transformer import Transformer

transformer = Transformer(
    model_name="my-model",
    instance_type="ml.m5.xlarge",
    instance_count=1,
    output_path="s3://my-bucket/output/",
)

transformer.transform(
    data="s3://my-bucket/input/data.csv",
    content_type="text/csv",
    split_type="Line",         # 1行ずつ分割して推論
)
transformer.wait()             # ジョブ完了後インスタンスは自動終了
```

### Lambdaで本番運用する場合のチェックポイント

以下が**全て**当てはまる場合に限り、Lambda で本番運用がしやすい

| チェック項目 | 目安・補足 |
|------------|-----------|
| モデルサイズが小さい | コンテナイメージ込みで数百MB〜1GB以内が目安 |
| CPU推論で十分な速度が出る | GPU非対応のためCPUで完結する軽量モデルに限る |
| 入力ペイロードが小さい | Function URLs の上限は **6MB** |
| レイテンシのSLAが緩い | コールドスタートで数秒〜十数秒のばらつきが許容される、またはProvisioned Concurrencyを有効化済み |
| 同時リクエスト数が少ない | アカウント上限1,000（リージョン共有）に収まる想定 |
| トラフィックが断続的 | 常時リクエストが来る場合はアイドル無課金のメリットが薄れる |
| MLパイプラインとの連携が不要 | SageMaker Pipelines / Model Monitor を使わない |

### Lambdaからサーバレス推論への移行ポイント

Lambda で運用を続けながら以下の兆候が出てきたら、**SageMaker サーバレス推論**への移行を検討する。
サーバレス推論はアイドル無課金・コールドスタートありとLambdaに似た課金モデルを持ちながら、SageMakerのMLエコシステムに統合されている。

| 移行を検討するトリガー | 理由 |
|----------------------|------|
| モデルサイズが 1GB を超えてきた | Lambda のコンテナ環境では扱いにくくなる。サーバレス推論はメモリ最大 **6GB** まで対応 |
| Model Monitor でドリフト検出をしたい | Lambda 単体では自前実装が必要。サーバレス推論なら統合済み |
| A/Bテストやカナリアリリースが必要になった | Lambda のエイリアス加重では管理が煩雑。サーバレス推論はバリアント機能で標準サポート |
| SageMaker Pipelines と連携したい | 再学習・評価・デプロイの自動化パイプラインを構築したい場合 |
| Provisioned Concurrency を有効化した | アイドル課金が発生し始め、コスト構造がサーバレス推論と同等以上になる |

> **注意**: サーバレス推論もコールドスタートは発生する。また、GPU非対応・最大メモリ6GB・ペイロード4MBの制約がある。
> GPU推論・常時高スループット・大ペイロードが必要になった時点で **リアルタイムエンドポイント** への移行を検討する。

### LambdaからSageMakerバッチ変換ジョブへの移行ポイント

Lambdaで推論を行いながら以下の兆候が出てきた場合、**リアルタイム性が不要**であれば **SageMaker バッチ変換ジョブ**への移行が最適解になる。
エンドポイントを常設せず、ジョブ実行時間のみ課金されるため、定期・一括処理ではコストが最小になる。

| 移行を検討するトリガー | 理由 |
|----------------------|------|
| 推論をリアルタイムで返す必要がない | バッチ変換ジョブは非同期一括処理。即時応答が不要なユースケースに最適 |
| 処理対象データが大量（数万〜数百万レコード） | Lambdaの15分上限・6MBペイロード制限では対処しきれなくなる。バッチはS3経由で制限なし |
| 定期スケジュールで予測を走らせたい | 日次・月次バッチをEventBridgeでトリガーする構成が自然。Lambdaで長時間処理をループさせるより安定 |
| モデルの更新後に全件再スコアリングしたい | 学習パイプライン（SageMaker Pipelines）の最終ステップとして組み込める |
| 推論結果をS3やDWHに書き出したい | バッチ変換ジョブの出力はS3に直接書き込まれるため、後段のETL・BI連携と相性がよい |
| GPU推論が必要かつリアルタイム性は不要 | バッチ変換ジョブはGPUインスタンスに対応。推論完了後に自動終了するのでコストも抑えられる |

**Lambdaバッチ処理との構成比較**

```
【Lambda によるバッチ処理（移行前）】

EventBridge → Lambda (15分上限・6MB制限)
  ↓ レコードをループ処理 (タイムアウトリスク)
  ↓ 結果を逐次書き出し
```

```
【SageMaker バッチ変換ジョブ（移行後）】

EventBridge → Lambda (ジョブ起動のみ) → SageMaker バッチ変換ジョブ
  ↓ S3の入力データを自動分割・並列推論
  ↓ 結果をS3に一括書き出し → 後段のETL・BIへ
```

> **注意**: バッチ変換ジョブはリアルタイム応答ができない。推論結果をAPIとして即時返す必要がある場合は、サーバレス推論またはリアルタイムエンドポイントを選択する。
